# 現代日本の郊外 プロシージャル生成

シードから現代日本の郊外の街を丸ごと生成し、Three.js で描画するデモアプリ。
戸建て住宅・2階建て外廊下アパート・RC中高層マンションに加え、駅前の商店街
（店舗併用住宅）と雑居ビル、幹線沿いのコンビニ、町外れの工業団地（折板屋根の
工場・倉庫）まで、**用途地域ごとに違う街**を生成する。

```bash
npm install
npm run dev        # http://127.0.0.1:5173
```

`npm run typecheck` / `npm run test` / `npm run build` / `npm run shot`

**操作**: 左ドラッグ=回転、ホイール=ズーム、右ドラッグ=パン。
`W` で**歩行モード**（WASD + Shift、`Esc` で解除）、
`C` で**走行モード**（W/S=アクセル・ブレーキ、A/D=ハンドル、Shift=速度上限を上げる、
Space=急制動、`Esc` で解除）。開発ビルドでは右上に lil-gui のパラメータパネルが
出る（シード変更・再生成、および全生成パラメータのスライダとデバッグ表示のトグル）。

デバッグ表示の**「用途地域（地区の塗り分け）」**は、工業帯がひと続きになっているか、
準工業が工業と低層住専の間に入っているか、そして**各用途地域が町の何割を取ったか**を
一目で確認するための層で、フラッドフィルと面積の天井が存在する理由そのものを検証する。
**「用途（敷地の塗り分け）」**は用途別に敷地を塗る。輪郭だけの層も別に用意してあるが、
「境界がどこか」ではなく「どれだけか」を見たいときは塗りのほうが速い ——
大きい地区と小さい地区は、輪郭では同じ1本の線にしか見えない。

```bash
npm run shot -- --zones commercial,industrial --kinds konbini,factory
```
用途地域は固定カメラでは見えない —— 商店や工場がどこに落ちるかはシードごとに違い、
商店街は**通りに沿って**見たときにしか商店街に見えない。`--zones` は各用途地域の
俯瞰と「その中でいちばん長い街路に立った視点」を、`--kinds` は指定した用途の建物を
一棟撮る。

## 設計の中核となる判断

**1. 「日本らしさ」は描くのではなく、法規を幾何制約として実装すると勝手に出てくる。**
建ぺい率・容積率・接道義務（幅員4m以上の道路に2m以上）・北側斜線・道路斜線・
910mm（半間）モジュール。これらを実際の制約として実装しているので、見慣れた
シルエットが自動的に生まれる。特に斜線制限は、あの階段状にセットバックした
中層の頭を数十行で作る。

**2. 建物フットプリント = 「ほぼ矩形の塊」を「建築可能領域でクリップしたもの」。**
これが「四角形以外の敷地にも自然に収まる」への答え。実際の不整形地の建物が
まさにこう設計されている。結果として「変な形の敷地に合わせる」が研究課題ではなく
**ブーリアン交差1回**（`building/footprint.ts` の `fitFootprint`）になる。
現在の設定で全建物の約25%が敷地形状によって実際に切り欠かれている。

**2b. ただし三角地では逆に、建築可能領域そのものを外形にする。**
斜め街路との交点にできる楔形の敷地では、矩形合成＋クリップは原理的に破綻する。
最大内接矩形は面積の約半分しかなく、膨らませてもフレームのバウンディング止まりで、
クリップするとその分がそのまま戻ってしまう。`minFloorArea` を割れば `null` を返し、
**その敷地は空き地のまま残る**（実測で全敷地の10%がこれだった）。
最大内接矩形が建築可能領域の `conformFillThreshold`(0.62) を割ったら、
建築可能領域そのものを外形として採用する（`conformFootprint`）。
鋭角の頂点は**隅切り**で面取りし、接道側の壁を固定したまま他の壁を内側へ押して
建ぺい率に合わせる。全ての壁が敷地境界と平行に走るので「敷地なりの建物」になる。
矩形が無いので切妻・寄棟は張れない。屋根は**陸屋根**（6割）か**片流れ**（4割）
—— どちらも任意多角形で厳密に張れる —— に落とす。全部を片流れにしていた頃は
それだけで町の 1/4 が片流れになり、しかも変形地は1つの街区に固まって出るので
同じ向きの三角屋根が並んでしまっていた。

**3. 直線骨格（straight skeleton）は使わない。**
フットプリントを「向きの揃った矩形の集合」として作るので、屋根は矩形ごとに
生成して相互貫入させてよい。L字の家は実際に2つの切妻屋根が谷で交わっている。
不透明ソリッドの相互貫入はブーリアン和と同じ絵になる。これで本プロジェクト
最大のリスク要因（凹頂点の split event、同時イベントの縮退、無限ループ）が消える。

ただし壁がクリップされた後は、屋根の矩形を**平面から describe し直す**必要がある
（`refitParts` / `describeAsRects`）。駐車スペースのノッチで平面がL字になるので、
外接矩形1枚だと車の上に4mの屋根が浮く。凹頂点で切って両脚を別々に記述する。

**判定は両側にかけないと意味がない。** 当初は「矩形の総面積が平面の1.35倍を
超えないこと」しか見ておらず、**屋根が平面を覆っているか**を見ていなかった。
短い脚が矩形として記述できないと、その脚は黙って `[]` を返し、長い脚だけに
屋根が架かって残りは**空に開いたまま**になる。しかも再帰の中では、片方を捨てた
分割は「無駄な面積」が小さく見えるので、正直な分割に**勝ってしまう**。
実測でスタックの5%、最悪の1棟は平面の62%に屋根が無かった。

記述できない断片は `[]` ではなく `null` を返し（`[]` は「屋根不要」と読める）、
片方でも `null` になった分割は捨てる。採用前に union が平面の97%以上を覆うことを
確認し、どの候補も通らなければ矩形なしと報告して片流れに落とす（任意多角形で厳密）。
`test/buildings.test.ts` が過剰被覆と不足被覆の両方を検証する。

**3b. 用途地域は「塗る」。用途は「導出する」。**
地区ごとに用途地域（商業・近隣商業・準工業・工業・住居系）を割り当て、その中で
既存の幾何ゲート（面積・接道長・道路の格）を効かせる。なめらかな場に閾値を切って
敷地ごとに判定すると工業が胡椒粒になり、工業団地は原理的に作れない —— 工業団地とは
「指定された連続した区域」であって「スコアの高い場所」ではないから。
詳細は後述の「用途地域」節。工業地域だけは街路の格子まで粗くする必要があるので、
**用途地域は道路生成の中で決まる**（本プロジェクトで下流が上流に手を伸ばす唯一の箇所）。

**4. 斜線制限は「階数の違い」で表現する。屋根の形ではない。**
建物平面を1〜3個の**スタック**（一様な階数を持つ領域）に分ける。北側斜線が効く
部分は階数がひとつ下がり、その上面は陸屋根＋パラペットの**屋上テラス**になる。
切断線は建物フレームの軸と910mmモジュールにスナップするので、段の稜線が壁と
平行になり「設計された段」に見える。
不変条件：高い領域はクリップで、低い領域は `differencePoly(before, after)` で
求めるので、`largest()` が非連結成分を捨ててもその成分は低いバンドに落ちるだけで、
**スタックの和は常にフットプリントと厳密に一致する**。

## パイプライン

```
seed
 └─ city/RoadSkeleton.ts  幹線・補助幹線・斜め道路を折れ線で（外周リングも）
    │  city/RoadDistricts.ts 骨格グラフの有界面 = 地区、境界道路から主軸を継承
    │  city/LandUse.ts       地区ごとに用途地域を割り当てる
    │                        （工業はフラッドフィルで連結した1塊として塗り、準工業で囲む）
    │  city/RoadGrid.ts      地区ごとに自前の直交格子（食い違い・行き止まり・軽い折れ）
    │                        ← 工業地域だけ格子が粗い。用途地域が街路に戻ってくる唯一の経路
    │  city/RoadClearance.ts リボンの重なりと鋭角交差を実測し、格下の区間を削除
    │  city/Roads.ts         上記のオーケストレーション → 平面化
    └─ city/Blocks.ts 平面グラフの最小閉路 → 街区ポリゴン
       │              （行き止まりの枝刈り、過大街区への街路の挿入）
       └─ city/Lots.ts   リング/コア分割 → 街路に直交してスライス
          │               → 私道・旗竿地 → 修復（接道保証）
          └─ city/Zoning.ts  urbanity 場 + 用途地域ごとの幾何的な適格条件
             │               → 用途（8種）と分譲地クラスタ
             └─ building/    envelope → footprint → mass → roof → facade → details
                └─ build/    チャンク × マテリアル系統でマージ
```

### 道路網 —— 地区ベースの階層モデル

実際の日本の郊外は、ひとつの街路網ではなく**区画整理された地区のパッチワーク**である。
各地区の内部はきれいな直交格子で、隣の地区とは幹線沿いでだけ角度がずれる。
局所的には整然、全体としては不規則。生成モデルもそのままその構造をとる。

**ひとつの格子をノイズで歪める方式では、これは作れない。** 直角を保てる程度に
弱い歪みは目に見えず、目に見える強さの歪みは全部の街路を曲げて家並みを扇状に
開かせる。だから街の不規則さは**地区の向き**が担い、地区の中の格子には触らない。

```
1. 骨格 (Tier-1)   外周リング + 幹線 + 補助幹線 + 斜め道路 → 平面化
2. 地区分割        骨格グラフの有界面 = 地区、主軸を境界道路から継承
3. 地区内格子      地区ごとの枠で直交格子（地区ごとに向きが違う）
4. クリアランス     非接続な辺の間隔と交差角を実測し、格下の区間を削除
```

**Tier-1 は折れ線である。** 本物の幹線道路は数百メートル直進してから一度きっぱり
曲がる。制御点ごとに独立した正規乱数を乗せてスプラインで均すのはランダムウォークで
あって道路ではなく、**街路の向きに違和感が出る原因そのもの**だった。ここでは頂点
3〜4個、1回の折れは `tier1MaxBend`（既定12°）が上限。骨格を置く時点で
「既存の Tier-1 と `tier1MinSpacing` 以内に並走しない」「`minJunctionAngle` 未満で
交差しない」を棄却サンプリングで満たす。

**斜め道路は Tier-1 に属する。** 完成した格子の上に重ねるのではなく、地区を*切る*。
だから格子は斜め道路で終端し、以前のように横切った街区が細片になることがない。

**地区の主軸**は境界辺の「長さ × 道路の格」で重みづけた mod 90° の円周平均
（`Σ len·w·e^{4iθ}` の偏角の1/4）。「最も長く接している道路から向きを継承する」の実体で、
極値2点に引きずられる OBB より頑健。そこに `districtAxisJitter` を足す —— 同じ幹線に
面した2地区が一続きの格子に見えてしまうのを防ぐ。

**地区の境界での扱いは方向で分岐する。** 素朴に地区を一律内寄せして格子を切ると、
幹線沿いに深さ4mほどのリボン状の裸地が全線にわたって残る。正しくは、境界道路に
**ほぼ直交する**街路は境界の中心線まで届かせ（接道はそこから生まれる）、
**ほぼ平行な**街路は境界から `localSpacing * 0.7` 以内なら線ごと捨てる
（幹線と最初の平行街路の間が、リボンではなく敷地2列ぶんの本物の街区になる）。

**日本的な癖は直交性を壊さない形で入れる。** 食い違い交差は格子点1個をずらすのではなく
**街路線を丸ごと**ある交差点から先だけ平行移動する（ノードをずらすと交わる4本が全部
曲がってしまう）。軽い曲がりは**必ず交差点を折れ点にする**ので、街区の辺は直線のまま、
1つの直線ランに面する敷地の接道方向は完全に一定 —— 道は折れて見えるが家並みは崩れない。
間引きと行き止まりはスパン単位。

### クリアランス —— 「接続していない道は触れてはならない」
以前は**接続していない2本の道路の間隔を測る処理がどこにも存在しなかった**。
`makePlanar` が解決するのは真の交差だけ、`PlanarGraph` がスナップするのはノード座標だけで、
1.5m離れて並走する2辺は完全に「平面的」に見える —— 幅13mの幹線と幅4.8mの街路が
実測3.5mまで接近し、7mぶんのアスファルトを共有していた。

`RoadClearance.ts` が検出器であり修正器でもある。`clearanceViolations()` は
**生成方法から独立**していて、テストが直接それを assert する（次に生成方式を変えても効く）。

肝は**交差点のマスク**。丁字路の両側にある同一街路の2辺はノードを共有しないが、
設計上たがいに幹線の半幅ぶんの距離にある。素直に測れば街中の交差点が全部「違反」になる。
そこで各辺を「そこで交わる最も広い道路の半幅 + クリアランス」だけ両端から切り詰めてから測り、
さらに**一方のノードが他方のノードの交差点半径に入っていればひとつの交差点の腕とみなす**。
これで本当に並走している2本だけが残る。

解決は貪欲かつ決定的に、**辺1本ではなくスパン単位**で削除する（街路の途中の1辺だけ
消すと穴になるが、スパンごと消せば正直な行き止まりが2つ残る）。両方が Tier-1 の場合は
何も消さない —— 骨格の棄却サンプリングがそこに来させないはずで、テストが落ちるのが正しい。

**私道も対象。** `Blocks.splitOversized` は過大街区を割る私道を街区面ポリゴンで切っていたが、
街区面の境界は道路の**中心線**なので、私道は両端とも境界道路のリボンに半幅
（幹線なら6.5m）食い込んでいた。`trimLaneEnds()` が右側後退線まで引き戻す。
`Lots.tryPrivateLane` の私道は `laneClears()` で検査する —— 行き止まりの街路は面の walk から
刈られるので**街区の内側に**いて、街区は道路のことを何も知らないまま私道をその上に通せてしまう。

### T字路の接続
`makePlanar` は端点に乗った交差を意図的に無視する。だから道路の中心線に**突き当たって
終わる**街路は、相手を分割できず、両者は接続されないまま残る。これは見た目の問題ではない
—— その街路は行き止まりとして面の walk から刈られ、その道路の両側の地区が黙って融合する。
`geom/planarGraph.ts` の `splitEdgesAtNodes()` が、辺の**内部**に乗ったノードで無条件に
分割してこれを塞ぐ。街路の側も接合部を少し行き過ぎてから交わり、外に出た切り株は
`pruneShortStubs()` が刈る。

### レイアウトのプリセット
`params.roads.layout` で切り替える（lil-gui の「街路のレイアウト」）。
**どちらも同じ生成器**で、地区がどれだけ互いに食い違ってよいかだけが違う。

- **`district`（既定）** —— 向きの違う地区が並び、行き止まりと食い違いがある。
  土地に合わせて開発が継ぎ足された郊外。
- **`grid`** —— 区画整理された計画住宅地。街全体でほぼひとつの向き、間引きも
  行き止まりもなし、斜めの通し道路2本。道路の格は**地区自身の格子線に割り当てる**
  （`promoteGridLines`）—— 別途うねる幹線を重ねると、横切った街区が全部細片になる。

切り替えは複数のパラメータを同時に動かすので `ROAD_LAYOUT_PRESETS` にまとめ、
`applyRoadLayout()` で一括適用する。

### 道路の敷地取り
道路の右側後退は**半平面クリップではなく道路の実フットプリントの減算**で行う。
半平面は無限に伸びるので、曲がった幹線に沿って10本以上の短い辺を持つ街区では、
凹側の各半平面が街区全体を横切ってしまい、面積2,000〜4,000m²の街区が丸ごと
空になっていた。減算なら局所的で、しかも `props/Ground.ts` が描く路面と
**同じ矩形**になるので、敷地と道路が構成上ずれない。

### 建物のできない敷地（空き地）
空き地は**理由とともに記録される**。以前は `buildBuilding` が素の `null` を返し、
`CityMesh` がそれを捨てていたので、街区の真ん中の禿げた土地に説明がなく、
そもそも生成器がそれを認識しているのかどうかも分からなかった。しかも判定は
**描画層の中**で行われていたため、`generateCity` しか呼ばない統計やテストからは
構造的に見えなかった（`kinds:` が常に敷地総数と一致していたのはそのため）。

いまは `planBuildings()` が描画から分離されていて、マテリアルもDOMも要らない。
`VacancyReason` は5種類：`no-buildable-area` / `buildable-too-small` /
`no-footprint-fits` / `too-narrow` / `not-attempted`。このうち
`UNAVOIDABLE_VACANCY`（`too-narrow`・`buildable-too-small`）だけが正当な結果で、
残りは生成器が使い損ねた土地を意味する。

**空き地を減らすのは段階的な譲歩**（`Builder.ts` の `CONCESSIONS`）。
セットバックを 1 → 0.6 → 0.35 → 0.15 倍、最小床面積を 1 → 0.8 → 0.55 倍と緩め、
途中で駐車スペースを諦める。奇妙な敷地を前にした実際の地主は、更地のまま残すより
小さい家を建てる —— セットバックと最小床面積はまさにそれを邪魔していた。
どの段でも建物が敷地の外に出ることはない（建築可能領域は常に敷地の内寄せ）。
勝った段のパラメータは**建物全体に通す** —— 一棟の中で2組のパラメータを混ぜると、
マスがその平面を分割しなくなる。

残るのは `too-narrow`（`footprint.ts` の内接円 < `module * 1.35` ≈ 1.23 m）だけ。
廊下より細い土地に建てるより更地のほうがよい、という意図的な拒否である。
デバッグ表示の「空き地（やむを得ない）／（要調査）」で色分けして現地確認でき、
`test/stats.test.ts` が理由別の内訳を印字する。実測 1.0〜1.3%、全てやむを得ない分。

この 1.0〜1.3% は 0.3〜0.6% から**意図的に上げた**数字である。後述の幅の下限を
クリップ経路にも適用した結果で、増えた分は以前 15.4 m × 1.8 m のような廊下型の
建物を受け取っていた敷地。**2 m 幅の土地に建てながら 2 m 幅の建物を出さない**
ことはできない。中央値で 32 m²・幅 3.3 m の切れ端であり、`too-narrow` は正直な
分類になっている。

### 建物と道路の重なり
**敷地が公道を含んではならない**、を一箇所で強制する（`Lots.ts` の `clipToRoads`）。
上流の各段は本来そうなるように作られているが、それぞれ別々に静かに失敗しうる：
未照合の街区辺はそもそも後退が入らず、`mergeCollinear` が2辺を併合すると片方の
幅員がもう一方に適用され、`differencePoly` は**クリッパが例外を投げると入力を
そのまま返す**（＝右側後退がまったく引かれていない街区が出てくる）。
経路ごとに塞ぐのではなく、**実際に描画されるのと同じ矩形**に対して最後に一度検査する。

加えて2つの構造的な修正：

- **行き止まりの街路は街区の「内側」にいる。** 面の walk から刈られるので街区の辺に
  ならず、しかし描画はされる。`Block.interiorRoads` として持ち回り、右側後退を引き、
  **両側を接道として売る** —— 行き止まりに家が並ぶのは、その道がある理由そのもの。
  `spurEdgeIds` は計算されて City まで運ばれながら、どこからも読まれていなかった。
- **リボンの端の張り出し。** 交差点の隅を埋めるための `half * 0.9` の延長は、
  行き止まりでは埋める相手がおらず、車道の 0.45 倍が背後の敷地に載っていた。
  次数1の節点では延長しない。

`test/overlap.test.ts` が両方を assert する。判定器は `Ground.addRibbon` の形状を
**張り出しの有無まで含めて**再現する必要がある（素朴な a–b 矩形では上の2件を取り逃す）。
面積は**交差ではなく差分**で測る —— リボンは交差点で互いに重なっていて妥当な
マルチポリゴンではなく、そのまま渡すと二重計上し、先に union すると失敗時に
入力をそのまま返して建物1棟丸ごとをアスファルト扱いにする。

### 建物の形 —— 針と廊下を落とす
複合マスを建築可能領域でクリップする（`footprint.ts` の ★ の行）と、両者は
**その敷地がたまたま持っている角度で**交わる。結果として髪の毛のような
フィンが残る —— 最悪のケースでは**リングが 1.4° で折り返して**おり、家の横に
剃刀が刺さっているように描画される。`cleanPolygon` にはこれが見えない：
スパイクの2辺はどちらも長いので `minEdge` が残し、先端の折れは 180° 近いので
`maxTurn` も残す。**鋭角の隅としてしか認識できない。**

`trimSharpCorners` が 45° より鋭い凸頂点を、**平面が2モジュール（1.82 m）幅に
なる位置まで**引っ込める。半平面でクリップするのではなく**頂点手術**で行う ——
1.4° の隅では切断平面は頂点から 60 m 先にあり、建物ごと持っていってしまうので、
既存の `chamferAcuteCorners` は「隣の壁を食う切断は行わない」と決めており、
**針とはまさにそれが拒否する隅**だった。頂点を動かす方は定義から局所的で、
面積を減らすだけなので建築可能領域から出られない。

角のない細さが2種類残る —— 短辺で切り落とされた楔（27 m の長さで 0.73 m まで
細る）と、建ぺい率合わせの壁後退が作る**5 cm の亀裂**。どちらも壁の背後に
どれだけ建物があるかとしてしか見えないので、`wallDepth` がレイキャストで測り、
細い平面だけが**モルフォロジー的オープニング**の代金を払う（20棟に1棟程度）。
膨張の頂点継手は円ではなく**建物自身の枠に沿った正方形**にしてある：円継手は
直角の隅に 0.41·r 届かないので、普通の家をオープンすると隅が 37 cm 削れ、
40 cm の壁パネルの扇が残る（16枚の壁 —— 玄関を置く場所すらなくなる）。

**幅の下限は 2.7 モジュール（2.46 m）。** これは新しい判断ではなく、
`conformFootprint` が以前から要求していた `module * 1.35` の半径そのもの。
新しいのは**クリップ経路も同じ基準で裁かれる**ようになったこと —— いびつな形を
作るのはクリップの方なのに、幅の検査が**まったく無かった**。3モジュールまで
締めると空き地がさらに19区画増える。2.46 m の家は細いが、家ではある。

順序が効く：**掃除してから切る**。逆にすると `cleanFootprintWithin` の
再クリップが落とした隅をそのまま戻すので、町で最も鋭い隅は 7° のままだった。
オープニングの後にもう一度切る —— 正方形継手は元の壁と好きな角度で出会うので、
放っておくと修復自体が 0.3° の針を作る。

`geom/offset.ts` の本物のバグも1つ落ちた。`boundaryBand` が帯を union して
返していたが、閉じたリングを一周する帯は**円環**であり、ここでの `Polygon` は
単一リングで穴を表現できない。結果として円環の外周＝多角形全体を覆う塊が返り、
`offsetInward` は**凹んだ平面はどれだけ広くても浸食で消える**と報告していた。
union をやめて重なったままの破片を返す（ブーリアン側が内部で union する）。

### 玄関の位置
**建物ごとに1枚の壁を選ぶ**（`chooseEntrance`）。以前の規則は「外向き法線が
街路方向から 57° 以内の壁」を壁ごとに独立に適用しており、これは3つ別々の間違い
だった —— 街路に面する壁が2枚ある建物は**玄関が2つ**になり（実測28%）、
駐車スペースの奥4mから街路方向を向いている壁が最前面の壁と同じ重みを持ち、
間口が 1.5 m に削られた家は「ベイに分割するには短すぎる」として**玄関が一つも
付かなかった**（40軒に1軒）。

`aim` が要件そのもの —— **道路または駐車場に向いていること** —— を表し、
`reach` が同点を街路に最も近い壁に倒す。長さは僅差だけを割るので、街路に正対する
短い壁は隣家を向いた長い壁に勝つ。ファサード側はこの壁**だけ**、それ以外では
何も得られないときだけ、コーナーリターンを詰めて 910 mm のドアを収める。

`test/shapes.test.ts` が両方を assert する。修正を外すと18テスト全部が落ちる ——
1.1° の隅、0.91 m 幅の平面、玄関が複数ある家が1シードあたり205〜277軒。

### 敷地分割 —— 最重要
**再帰OBB分割は意図的に使っていない。** 教科書的な答えだが接道が保証されず、
内部の区画が landlocked になる。日本ではそれは見た目の問題ではなく、
接道義務を満たさない土地には文字通り建てられない。

代わりに、接道辺から敷地奥行ぶんのリングを剥がし、そのリングを街路に直交して
スライスする。街区中央に残ったコアには私道（位置指定道路）を通すか、旗竿地の
竿を出す。**生き残った敷地はすべて構造上、接道している。**
`test/lots.test.ts` がこの不変条件を検証する。

**端切れは捨てずに敷地として残す。** 却下の閾値は `minLotArea`(10 m²) と
`minFrontage`(1 m) と `minInscribedRadius`(0.9 m)。実際に効いているのは
最後の内接円で、`minLotArea` だけ下げても何も変わらない —— 3×4 m の隅は
12 m² あるが内接円は半径 1.5 m しか入らない。`minFrontage` は接道義務の 2 m を
**下回る**値にしてある。道路の拡幅が残した角のような**未接道**の端切れが
実際の郊外には必ずあり、却下すると街に穴が空くため。ただし例外であるべきなので、
`test/lots.test.ts` は全敷地の 95% 以上が 2 m を満たすことを確認する。

区画は自分が切り出された接道参照を持ち歩く。私道の奥の区画は街路ではなく
**私道に接道**しているので、街路参照だけで判定すると全部落ちてしまう
（私道を掘って舗装した上で、その私道が奉仕するはずの敷地を全部捨てていた）。
街区の参照も併せて適用するので、角地はきちんと2面接道になる。

## 用途地域 —— 敷地ごとではなく地区ごとに決める

**なめらかな場に閾値を切ると、胡椒粒しか出てこない。** 最初に考える方法は
urbanity 場に「工業度」の軸を足して敷地ごとに判定することだが、これは原理的に
破綻する。等高線の近くの敷地が一つずつ独立に裏返るので、工場が家と家の間に
挟まり、領域の縁はぼろぼろで飛び地が散る。しかも縁を消すほど場を滑らかにすると、
今度は領域に境界そのものが無くなる。

**工業団地とは「工業スコアが高い場所」ではなく「そう指定された連続した区域」であり、
指定が先にある。** だから `city/LandUse.ts` はそう塗る —— 地区の隣接グラフの上で
種を選び、面積の目標に届くまでフラッドフィルし、結果を準工業で囲む。
連結性は調整の結果ではなく**構成上の帰結**になり、`test/landuse.test.ts` が
それを検証する。

地区の面はもともと正しい単位である。都市計画図はその上に描かれているし、
地区ひとつが区画整理ひとつぶんの格子を持っている。

**幾何ゲートは地域の中で引き続き仕事をする。** 近隣商業はコンビニを*置かない*。
幹線沿いにたまたま広くて浅い区画があったときに、コンビニを*可能にする*だけである。
`maxLotAreaMajor` が用途配分にマンションと一言も書かずにマンションを可能にしているのと
まったく同じで、これが崩れると「用途地域が建物を配置する」ことになり、
この生成器の作り方から外れる。

### 地区は粗く、そして不揃いである（実測）

設計時の見積もりは外れた。`extent: 320` の実測は:

| | 地区型 | 格子型 |
|---|---|---|
| 地区数 | 13 | 9 |
| 面積 p10 / p50 / p90 / max | 2,272 / 19,194 / 80,871 / **104,676 m²** | 2,364 / 44,997 / 97,157 / 97,157 m² |

町全体が 409,600 m² なので、**最大の1地区だけで町の 25%** を占める。よって
ここでの判断はすべて**個数ではなく面積**で行う。「一番よい地区を2つ」は
町の 8% と 40% のどちらにもなりうる。

同じ理由で3つの安全弁が要る:

- **種は地区ではなく連結成分から選ぶ。** 外れ値のスリバー（斜め道路2本と補助幹線に
  挟まれた面）は町の端にあるので工業スコアが高く出る。それが自分だけの成分を
  作って隣が全部ブロックされ、指定工業地域が 0.0% になった町があった。
  種の面積に下限を設けるのは逆効果で、大きな成分の縁にある小さな地区は
  出発点として何も悪くない —— それを禁じたら別の町が工業の三分の二を失った。
- **成長にも上限を要る。** 上限が無いと、1万 m² の不足を埋めるために 105,000 m² の
  隣を平気で併合して 38% まで行き過ぎる。
- **商業にも面積の天井を要る。** 半径だけでは何も縛れない。町が小さくなっても
  地区は小さくならないので、`extent: 190` では商店が地図の大半に届き、
  全敷地の四分の一が店舗併用住宅になっていた。

### 満たせない条件と、満たせる条件

「工業地区のどの部分も駅から 260 m 以内に来ない」——
きわめて妥当に見えるこの規則は、**この分割では一つも指定できない**。
地区は数百 m の差し渡しがあるので、平均的に遠い地区でも町の中心へ手を伸ばす。
実測で、駅から最も遠ざかる地区境界でも格子型で 217 m しかない。

**この粒度が実際に約束できるのは「商店の隣ではないこと」**で、しかも
用途地域図が気にするのはそちらである。重心距離の下限と、商業核とその隣接からの
除外 —— この2つで表現する。

### 用途地域が街路の粗さを決める

工場用地は 3,000〜4,000 m²。住宅地の 45 m 格子が生む街区は 1,500〜2,000 m² で、
**敷地パラメータをどう弄っても工場用地は出てこない。** だから用途地域は
`generateRoads` の**中**、Tier-2 の格子を敷く前に決まる。本プロジェクトで
下流の概念が上流に手を伸ばす唯一の箇所であり、避けようがない。

街路を粗くするだけでも足りない。`Blocks.maxArea`(5,200) が 95 m 間隔で切り出した
12,000 m² の面に街路を通してしまい、三分割された 4,000 m² の街区と一緒に
工場用地も消える。**格子と街区上限は同じ「工業街区の大きさ」に同意していなければ
ならない。**

### 長屋は側面セットバックを 0 にするだけ

店舗併用住宅が隣と壁を接するのは `setbackScale.side = 0`、それだけである。
建築可能領域のパイプラインは端から端までセットバック駆動なので、0 は
建築可能領域・フットプリントのクリップ・`Wall.room`・軒のクランプ・
バルコニー抑止・境界の塀に**そのまま無料で伝播する**。

`sharesWallWith` のようなフラグにすると、この全部を作り直すことになる。
しかもそのフラグは嘘になる —— 隣接敷地は独立に生成されるので、`cleanPolygon` の
あとで側面境界が厳密に共線である保証がない。**境界まで建てる**が正直で疎結合な
言い方で、残る隙間はミリ単位である。

正面だけは 0 ではなく 0.32 m にしてある。`clipToRoads` が既に側溝ぶん 0.5 m を
空けているので余裕を持って安全だが、0 だと「道路上に建てない」検査が
クリーンアップの許容差とのコイン投げになる。

### 北側斜線は住居系の地域にしかない

工業地域の工場と商業地域の雑居ビルには北側斜線がかからない。これは近道ではなく
法的事実で、「法規を幾何制約として実装する」という本プロジェクトの主題そのものである。
副作用として、20 m の倉庫が「背後の家の日照のために書かれた規則」で階段状に
刻まれることも無くなる（`mass.ts` は 2 階未満なら斜線カットを丸ごと飛ばすので、
背の高い平屋はもともと無傷だった —— それを偶然ではなく意図にした）。

### 商店街は「地区」ではなく「通り」である

用途のゲート調整でいちばん時間を使った点であり、間違いはすべて同じ形だった。

- 幹線接道を要求 → 商店は商業地区の**外縁だけ**に張り付き、町に5軒。
- 道路の条件を外して用途地域だけを信じる → この粒度では近隣商業＋商業が地図の
  五分の一なので、**町の 21% が一続きの商店街**になった。

効いたのは**地域ごとに違う問いを立てる**こと。商業地域の中では区画の形が
すべての条件である（裏通りが戸建になる商業地域は商業地域ではない）。
近隣商業では、それに加えて幹線であるか駅に十分近いことを要求する。

## 繰り返しを目立たせない

避けるべき失敗モードは、一様ランダムが生む「ノイジーなランダム」。遠景では
逆に均質（全部が同じ灰色の粥）に、近景では非現実的（1975年の家にガラス手すりと
片流れ屋根）に見える。効果の大きい順に：

1. **相関するスタイルベクトル**（`building/style.ts`）。建物ごとに
   `era` / `wealth` / `formality` の**3つの数だけ**サンプリングし、屋根材・外壁材・
   窓の縦横比・手すり形式・彩度・軒の出・面格子の有無など20個のパラメータを
   そこから**導出**する。ありえない組み合わせが原理的に生成されない。
   `era` は二峰性分布（1975–1990 と 2000–2020）—— 実際の街には世代の波がある。

   アーキタイプが持てる屋根形式は**重み付きリスト**で、一様に引かない。
   片流れは手続き生成で最も過剰に出る屋根で（任意多角形で厳密に張れるから
   フォールバックが全部そこに向かう）、並ぶと「生成物」に見える。
   重みと `conformFootprint` の陸屋根化を合わせて、実測 25% から 12% に落とした。
2. **分譲地クラスタ**。隣接する3〜8区画がスタイルベクトルをσ1/6で共有する。
   これは意図的に**ほぼ同一の繰り返しを再導入する**。日本の郊外は実際にそう
   見えるから——同じ建売が5棟並び、次に古い雑多な区間があり、また別の並びが来る。
   結果として残った繰り返しが「バグ」ではなく「意図」に見える。
3. **上下階の開口の整列**（`building/facade.ts`）。上階の開口は80%の確率で
   下階と同じモジュール位置に置かれる。窓が縦に揃っていないのは素朴な手続き
   ファサードの最大の弱点。
4. **パレットの規則**（`material/palettes.ts`）：屋根の明度は 0.72 以下か
   壁より 0.08 以上暗いこと／屋根の彩度は**絶対上限**0.74／2トーン壁は1F/2Fの境で
   分け70%は暗い方が下。色は必ず HSV でジッタする（RGB一様ジッタは灰色に寄って
   濁る）。パレットは重み付き——一様に引くと街の1/5がガルバ黒になってしまう。

   屋根の色の配合は `buildings.roofHueMix` で**設定できる**。赤錆茶／紺／銀黒／
   茶／青緑の5系統に何割ずつ振るかで、上空から見た町の印象がまるごと変わる
   ——本プロジェクトで最も効く1つの設定なので、テーブルに埋めずに GUI に出した。
   既定は 赤錆茶22 / 紺18 / 銀黒38 / 茶12 / 青緑10。

   **系統を先に引いてから、その系統の中で色を引く。** 逆にすると設定が守られない
   ——次項がその話。

   ### 屋根色の判定が重みを食い荒らしていた

   `sampleRoofColor` は条件を満たす**最初の**候補を返すので、**弾かれた色の重みは
   通った色に流れ込む**。これを2回踏んでいる。

   1回目、屋根の彩度を**壁との相対**（`彩度 < 壁の彩度 + 0.1`）で判定していた。
   壁は彩度0.1前後の淡いベージュなのに実際のコバルト瓦や赤錆屋根は0.5前後あり、
   色付きの屋根はすべて落ちてフォールバックで彩度を潰され、**街中の屋根が炭色
   一色**になった。絶対上限に変えて直した——**つもりだった**。

   2回目、その絶対上限を 0.52 に置いた。赤錆茶は 0.565、その濃い方は 0.552。
   **最も重い2色がどちらもわずかに超えていて、常に弾かれていた。**
   さらに明度の条件 `壁の明度 − 0.15` を、タウプや吹付タイルの壁が赤錆茶の下まで
   押し下げる。残るのは紺と銀黒だけ——重み 11% の紺が実測 **48%** を占め、
   重み 56% の赤錆茶が **13%** しか出ていなかった。「紺が多い」のは
   パレットの重みではなくフィルタの症状で、重みをいじっても直らない。

   **上限を緩めるだけでは足りない。** 上限を上げると今度は赤錆茶が重みを
   食い荒らし、赤系が 46% になった。フィルタが1枚のパレット全体にかかる限り、
   通りやすい色が通りにくい色の重みを吸い上げる構図は変わらない。

   **系統を先に引く**のが解。`roofHueMix` から系統を1つ選び、その系統の中の
   色だけを候補に立てる。棄却は同じ系統の中で色を差し替えるだけになり、
   系統をまたいで重みが動かなくなる。両方の上限もテーブル内の全色を通す値
   （彩度 0.74 / 明度 0.72）に上げた——上限の役割はジッタの裾を切ることであって、
   パレットに拒否権を持つことではない。

   実測（`test/buildings.test.ts` の `roof colour` 行、勾配屋根のみ）：

   | | フィルタ修正前 | 上限だけ緩めた版 | 系統先引き（現在） | 設定値 |
   |---|---|---|---|---|
   | 赤錆茶系 | 13% | 46% | 25% | 22 |
   | 紺系 | 48% | 25% | 20% | 18 |
   | 銀黒系 | 28% | 21% | 38% | 38 |
   | 茶系 | — | — | 7% | 12 |
   | 青緑系 | 12% | 8% | 11% | 10 |

   茶系だけ設定を下回るのは、瓦のパレットに茶がなく、瓦の分がほかの系統に
   再配分されるため。それ以外は設定どおりに出る。

   計測側にも罠がある。系統は色相で分離できない——赤錆茶と茶は色相で4°しか
   離れておらず、銀黒は**青い色相を持つグレー**なので HSL 彩度で切ると紺に
   分類され、紺が 43% に見える。ジッタ幅は色相 ±0.015 と swatch 間の隙間より
   十分小さいので、**最も近い swatch を引き当てて**その系統を数えるのが正しい。

## 街を走る

用途地域が生むものは「1本の通り」ではなく、**住宅街を抜け、商店街を過ぎ、工場に着く**
という数百メートルの体験である。それは歩くと長く、走ると短い。だから3つめのカメラ
モードは「速い歩行モード」ではない。

- **横移動ではなく操舵する。** その場で振り向けないので、曲がる前に近づく必要がある。
  これが「浮いたカメラ」ではなく「車」に感じられる唯一にして最大の要素で、
  操舵の効きは速度に比例させ、停止時はゼロにしてある。
- **速度を持ち越す。** アクセルを離すと惰性で転がる。上限は生活道路で約31km/h、
  Shift で約58km/h。S はブレーキ、停止後はバック。
- **視線は独立している。** 走りながら店先を眺められることがこのモードを作る理由の
  半分なので、マウスの視点操作はそのまま効く。操舵は視線を同じ角度だけ回すだけで、
  上書きはしない。

**建物には当たる。** 歩行モードだけの頃はすり抜けても許容範囲だった —— 4m/s で
壁に入るには入る気が要る。走行モードではそれが常態になり、100m が数秒で過ぎるので、
当たり判定が無いと車は町の「上」ではなく「中」を走ることになってモードが成立しない。
建物フットプリントを一様グリッドに入れて点で判定し、進めないときは軸ごとに
分解して再試行する —— これが無いと角をかすっただけで完全停止し、正しくても
バグに感じる。実測で、全開走行20秒（1,200ステップ）中の建物内侵入は 0 回。

塀・フェンスは通り抜ける。敷地の中には入れるので、コンビニの駐車場にも
工場のヤードにも乗り入れられる。

## 決定性

**すべての生成関数は `Rng` インスタンスではなく「シード文字列」を受け取る。**

```
"sakura-3/block/17/lot/4/facade"
```

これにより生成が順序非依存になる：1棟だけ再生成してデバッグできる、後から
Worker 並列化できる、新しい小物を1種類足しても他の全建物の見た目がズレない。
1つの `Rng` を引き回すと、どこかに `rng.next()` を1行足しただけで街全体が別物になる。

## 幾何ライブラリ

`polygon-clipping` のみに依存し、内側/外側オフセットは自前でその上に構築している
（`geom/offset.ts`）。素朴なマイターオフセットを試し、**結果を検証してから**採用し、
自己交差した場合は「境界からの距離がd未満の帯」をブーリアンで引くという厳密な
構成にフォールバックする。

`geom/boolean.ts` のラッパは**戻り値を必ずクリーンアップしてから返す**。ブーリアンは
共線頂点とミリ単位のスリバーを吐き、それがファサード生成まで到達すると長さゼロの
壁パネル → NaN 法線 → チャンクごと消失、という追跡困難な不具合になる。
`polygon-clipping` が稀に失敗する入力に対しては、座標を段階的に量子化して
リトライする（`QUANTA`）。

建物のセットバックは辺ごとに幅が違うので、オフセットではなく**半平面クリップ**の
交差で行う（敷地は凸に近いので正確で、かつ安い）。街区から道路を取る側は逆に、
半平面では曲線道路の凹側で破綻するため**実フットプリントの減算**を使う。

ただし敷地も凹になることがある（L字の残地、旗竿地の奥）。凹頂点の裏に隠れた辺の
半平面は敷地を横断してしまうので、辺が十数本あると交差が消滅する。実測で1町あたり
28敷地（最大513m²）が**建築可能領域ゼロ**になり、そのまま空き地として残っていた。
半平面が潰れた場合のみ `offsetInwardVariable`（辺ごとの幅を持つ内側オフセットを
**帯の減算**で行う、`geom/offset.ts`）へフォールバックする。凹でも正しく、
成功している敷地は経路に入らないので出力が変わらない。

## 庭の量と、建物の敷地内での位置

庭は設計していない。**セットバックとフットプリントの引き算の残り**である。
だからどこで面積が落ちているかを把握していないと、意図せず庭だらけになる。

**駐車スペースは「間口全幅の帯」ではなく「隅の矩形」。** 以前は正面セットバックに
車1台ぶんの奥行を足していたので、間口の全幅が下がっていた。車が要るのは幅2.5mで、
間口はその3倍あることが多い。中央値の敷地で約17%、間口が広い敷地ではもっと
捨てていた。今は幅 `carPadWidth` × 奥行 `carPadDepth` の矩形を接道側の隅に置き、
建築可能領域から引く。駐車場に離隔義務はないので敷地境界にぴったり付ける
（側面セットバック帯と重なるぶん、建物から削る量が減る）。
建物の平面はこれでL字になる —— 駐車スペースを囲む形は、狭小地の実際の解そのもの。
アーキタイプ側のノッチ（L/T）は駐車スペースがあるときは付けない。二重に
同じ理由で削ることになるため。

**建ぺい率だけでは庭は減らない。** `targetArea = min(敷地×建ぺい率,
建築可能領域×footprintFill)` で、セットバックが十分に取ると第2項が必ず勝つ。
つまり GUI の建ぺい率を上げても何も起きない状態が起こりうる。庭の量を実際に
決めているのは **`footprintFill`** なので、これも GUI に出してある。

**建物は北側の境界に寄せる。** 左右の余りを均等に分けると、使えない0.8m幅の
隙間が両側にできる。北に寄せて余りを南に集めると、南向きの庭がひとつできる。
駐車スペースは反対（南）の隅に置くので、駐車と庭が前面でつながる。

`carPad` はかつて `differencePoly([敷地], [建築可能領域])` で作っていた。
建築可能領域は敷地の内側に完全に収まるので差はドーナツになり、
`geom/boolean.ts` は穴を設計として捨てる —— **結果は敷地そのもの**だった。
そのため車は敷地の重心（＝家の中）に停まり、`buildPlanting` は敷地全体を
植栽禁止領域とみなして、駐車場付きの戸建て（82%）に植栽を1本も置いていなかった。
実測でドーナツ警告291件に対し駐車場付き敷地279件。

## 張り出しと敷地境界

バルコニー（1.0〜2.1m）、外廊下（1.1〜1.8m）、軒の出（最大0.86m）はいずれも壁から
張り出すが、側面セットバックは民法234条の0.5mしかない。`Wall.room` が
「その壁が敷地境界まで何m張り出せるか」を持ち、バルコニー・外廊下・軒の出は
そこで頭打ちになる。余裕がない壁にはバルコニーを付けず窓だけにする ——
実際の狭小地の家がそうしている。

## 描画についての注意

`MeshStandardMaterial` の間接光は空から生成した PMREM 環境マップが担う。これが
ないと街全体が「フラットシェーディングのブロックの集まり」に見え、ガラスが
ガラスに見えなくなる。

PMREM は half-float テクスチャを線形フィルタでサンプルするため
`OES_texture_half_float_linear` を要求する。**ソフトウェアラスタライザ
（SwiftShader、ヘッドレス撮影で使われる）はこれを公開しておらず、サンプル結果が
黒になってシーン中の全マテリアルをゼロにしてしまう。** 実機の GPU はすべて
対応しているが、非対応環境では自動的に検出して、環境マップの代わりに強めの
hemisphere ライトとより拡散的なガラスにフォールバックする（`app/Environment.ts`、
`material/materials.ts`）。`npm run shot` の出力はこのフォールバック経路である点に注意。

影のシャドウカメラは毎フレーム、シャドウテクセル単位にスナップしている。これを
やらないと視点移動時に影がチラチラ這って、原因不明のまま安っぽく見える。
